# MiOpIIk 0.5：DSH 吸收清单与重定位

> 决策文档。判定对象 = 本机实际安装并运行的 DSH `0.2.0-rc.2`（npm `latest` 同为 `0.2.0-rc.2`，`alpha` 通道 `0.2.1-alpha.2`）。
> 每条判定都带可复核证据。取证手段：`README.md` / `lib/types/*.d.ts` / 源码，外加**活运行时** `cordis_inspect_query(host, Tool, listTools)` 取「当前模型可见工具全集」——这是区分「宿主能力」与「模型可见面」的第一手判据。

## 1. 一句话结论

DSH 已经把 MiOpIIk 原来的**运行时机制**整块吸收；MiOpIIk 剩下的真实空档只有「**DSH 有原语、但模型调不到**」的那一层。0.5 据此把 9 个包砍到 2 个、10 个模型可见工具砍到 5 个。

## 3. 逐项判定

判定口径：**完全冗余** = 语义完全覆盖、可整条删除；**部分冗余** = 原生覆盖主干、插件只剩一个可指名的真实增量；**独有** = 原生确实没有。判定必须区分「宿主能力」与「模型可见工具」——「宿主有 `sessions.fork`」≠「模型能 fork」。

| 能力 | 原生等价物 | 判定 | 处置 |
| --- | --- | --- | --- |
| `agent_checkpoint` | 无「命名恢复点」语义 | **独有** | 保留 |
| `agent_rewind` | 仅有 fork 原语，模型面缺失 | **独有** | 保留 |
| `agent_rule_*` | `systemPrompt.section` 是插件 API；`AGENTS.md` 是持久+全局语义 | **独有** | 合并为 `session_rule(action)` |
| `agent_checkpoint_list` | 原生 `read` 可读同一文件 | 部分冗余（增量：格式过滤） | 保留（近零成本） |
| `agent_checkpoint_prune`（已并入自动裁剪） | 原生 `write`/`edit` | 部分冗余（增量：只删可解析行 + CAS） | **合并**进 `agent_checkpoint` 的自动裁剪 |
| auto-checkpoint 事件钩子 | 持久化 + `session_*` 检索覆盖主干 | 部分冗余（增量：项目本地逐轮一行可 git diff 的索引） | 保留（无工具面） |
| `session_doctor(seams)` | `cordis_inspect_*` 覆盖 API 形状 | 部分冗余（增量：**实调证据** + 落盘共享清单 + 启动自动探测） | 保留，合并为 `session_doctor(seams)` |
| `session_doctor(stats)` | `tokenUsage` 投影存在但无模型面 | 部分冗余（增量：**模型可见入口**本身） | 保留，合并为 `session_doctor(stats)` |
| `mop_learn`（**已删除**） | `write` + `dsh-skill-filesystem`（写后即入目录） | 部分冗余（增量：写入校验 + 防覆盖） | **删除** |
| `dsh-miopiik-policy` | 原生 `modelSelectionSettings` + `allowedModels` 白名单；无「必须显式选路由」模式 | 部分冗余，且**触发面为空转**（见 §4.1） | **删除**（它守的是 preset 里的行，不是能力） |
| `dsh-miopiik-magic-keywords` | 上游零命中 | **独有**，但属提示注入**偏好**而非能力空档 | **删除**（产品取舍） |
| `dsh-miopiik-capabilities` / `-run-stats` | 本仓库 `-diagnostics` 的纯 re-export | 完全冗余 | **删除** |

## 4. 两处需要特别说明的判定

### 4.1 `dsh-miopiik-policy` 为什么最终删除

`subagent_execute` **不是**虚构名——它是 MiOpIIk preset 自己定义的派发实例（`toolName: subagent_execute`）；原生 `dsh-tool-subagent` 的 `toolName` 默认值是 `subagent`，且派发工具按实例 `toolName` 生成。所以守卫是「**preset 耦合**」的：只在运行旧 MiOpIIk preset 的会话里生效。

0.5 起 preset 不再由本套件代管（DSH 的 preset 是声明行），那个行随之消失 → **守卫默认空转**。按原生优先原则：**「为不存在的行准备的守卫」就是重叠面，应当删除，而不是留着占位。** 需要「必须显式选路由」时，用 DSH 原生的 `modelSelectionSettings` + `allowedModels` 白名单。

这条判定本身是一次自我纠偏：本文件早先版本判它为「保留」——理由是「成本低、以后可能用得上」。那是**为将来假设保留代码**，正是本轮要清理的坏习惯。

### 4.2 刻意不覆盖 `spawn_teammate` / 原生 `subagent`

不是「懒得做」，是取证后判定**没有最小且不误伤的判据**：

- `spawn_teammate` 的 schema 只有 `name` / `description` / `prompt`（必填）+ `context`（可选，`fresh|fork`，省略即文档化的 fresh）。子代理路由来自插件配置 `freshProvider` / `forkProvider`，**调用方没有 provider/model 可强制**。把「必须显式传 context」当判据会拒绝上游文档化的合法调用。
- 原生 `subagent` 的 description 明写路由可整体省略以继承默认；半传（只传 provider 或只传 model）上游自己就抛 "must be supplied together"。强制显式路由会拒绝合法调用，半传判据则是重复上游校验。

守卫纪律：**宁可少拦，绝不误拦**。

## 5. 新定位

### 5.1 判据（先立尺子，再定位）

「不重叠」不能靠感觉。DSH 的定式是**原语（Service/API）与模型面（Tool）分离**，而且分离是**刻意的**，不是遗漏——上游 README 自己写明：

| DSH 的能力 | 原生模型面 | 上游的明示 |
| --- | --- | --- |
| `sessions.fork` 原语 | 无（只有 Web GUI 按钮） | 三层调用者全是宿主/客户端 |
| `systemPrompt.section` 注册 | **无** | `dsh-system-prompt` README：「there is no end-user prompt-editing API」 |
| `tokenUsage` / `sessionStats` 投影 | **无** | 「registers nothing model-facing」 |
| `cordis_inspect_*` | **有** | —— |

所以「补一层 Tool」本身是正当的，但**必须承认它是在给一个刻意关闭的门开缝**，因此：

1. 只开确实需要的缝，缝要窄到不可再窄；
2. 永不复制原语——只调 `ctx.*`；
3. 退场条件写死在文档里，上游一开即拆。

### 5.2 定位陈述

> **MiOpIIk 不是一个功能插件，是一层「策略到执行的适配层」。**
>
> - **策略**（本体）：用户的工作纪律——证据优先、授权闸、成本敏感、独立验收——写在 preset / persona 与 DSH 原生配置里。**这部分不写代码**，它才是 MiOpIIk 不可替代的东西。
> - **适配**（本插件）：DSH 刻意保持「有原语、无模型面」的少数几处，给模型开一条窄缝。每一处都必须能用一句「DSH 有 X，模型调不到」说清；说不清就不该存在。

换句话说：**插件是策略的适配器，不是能力的提供者。** 任何「DSH 没有所以我实现一个」的冲动，先反问一句「上游是不是刻意不做」——是，就别做。

### 5.3 当前承接的缝（5 条，每条都要能一句话说清）

| 缝 | DSH 有 | DSH 没有 | 承接方式 |
| --- | --- | --- | --- |
| 命名恢复点 | fork 原语 + 会话事件流 | 模型调不到 fork；没有「给某一轮命名 + 持久索引」 | `agent_checkpoint` / `agent_checkpoint_list` |
| 回溯 | `sessions.fork(source, boundary)` | 同上 | `agent_rewind` |
| 会话级规则 | `agent.ctx.systemPrompt.section()` | **刻意无 end-user 编辑 API** | `session_rule` |
| seam 可用性证据 | `cordis_inspect_*` 查 API 形状 | 不能调业务方法 → 拿不到 invoked-ok | `session_doctor(seams)` |
| token 用量读数 | `tokenUsage` 投影 | 无模型面 | `session_doctor(stats)` |

**后两条是次要的**：它们不是「上游刻意关闭」而是「上游只服务客户端与压缩器」。`session_doctor(stats)` 严格说是在给一个既有读数加一个模型面视图——保留理由是成本极低且评测门需要，**不是因为它填了能力空档**。若哪天要做最激进的收缩，先删它。

### 5.3.1 「一个集合」是不是牵强 → 按共享状态切分

用**共享状态**而不是「都在这个仓库里」判定集合性，5 条缝自然分成两组：

| 组 | 共享状态 | 成员 |
| --- | --- | --- |
| 会话的命名恢复账本 | `.dsh/memory/checkpoints.md`（4 个成员都读写同一文件） | `agent_checkpoint` / `agent_rewind` / `agent_checkpoint_list` + auto-checkpoint 钩子 |
| 会话级规则 + 诊断 | 无共享文件（规则是会话内存态；诊断各自落 `capabilities.md` 或读投影） | `session_rule` / `session_doctor` |

所以拆成两个包，而不是「一个包塞 5 个工具」。**切分依据是共享状态，不是功能数量。**

- `dsh-agent-rewind`：账本组。**通用**——任何 DSH 用户都用得上「给某一轮命名 + agent 自己回溯」，与 MiOpIIk 工作流无关，故独立成包、名字不带 miopiik。
- `dsh-session-policy`：规则 + 诊断组。MiOpIIk 特性。
- `dsh-session-policy` 依赖 `dsh-agent-rewind`，保证一条 `add` 装齐。

**命名对应关系**（消灭历史上的 `mop_` / `miopiik` 双缩写）：

| 层 | 名 |
| --- | --- |
| 项目（persona / preset） | MiOpIIk |
| 包 | `dsh-agent-rewind`、`dsh-session-policy` |
| 工具 | 前缀 = 所属包职责：`agent_*`、`session_*` |

工具名用 `agent_*` / `session_*` 而非裸名，是因为 `checkpoint` / `rewind` / `rule` 都是普遍词、裸名易与其他插件撞名；而 `session_search` / `session_event_read` 正是 DSH 自己的先例（包 `dsh-tool-session-query` → 工具 `session_*`）。

**为什么包名不叫 `agent-rewind`**：npm 上已被占用，且占它的项目概念高度重合（`agent-rewind@0.2.0` — *"Flight recorder + undo button for AI agents"*）。`agent-checkpoint`、`agent-recall` 同样已被占用。按「不代替已存在的」原则，加 `dsh-` 前缀区分。

### 5.4 退场条件（写进 README，必须遵守）

- DSH 给 `sessions.fork` 加模型可见工具 → `agent_checkpoint` / `agent_rewind` / `agent_checkpoint_list` 整体删除。
- DSH 开放会话级提示编辑入口 → `session_rule` 删除。
- DSH 给 token 投影加模型面 → `session_doctor(stats)` 删除。
- DSH 提供「必须显式选路由」的模式 → `dsh-miopiik-policy` 删除（当前它已默认空转）。
- 需要跨会话检索 → 那是 opt-in 官方包 `@deepseek-ai/dsh-tool-session-query` 的事，不由本套件代管。

**每次 DSH 版本升级的标准动作**：重跑 §2 证据核对，被吸收的条目删除，不留兼容层。这是「原生优先」在流程上的落实。

### 5.5 不进入的领域

以下都属于 DSH 已经**正面提供**的能力，本插件永不实现，即使看起来「可以做得更好」：

子代理派发与生命周期、Agent Teams 协作与任务板、模型授权与白名单、会话持久化与崩溃恢复、会话检索与 trace、技能目录/发现/加载、沙箱与审批策略、权限预设、压缩与上下文管理、计划模式、目标与 todo、工作流编排、Ralph 循环、插件清单与配置编辑。

判据同上：**上游已经做了，做得差也是上游的事。**

## 5.6 「就这些，是不是太简陋」

这是本设计最该正面回答的问题。答案是：**代码确实极小，但把「插件」当成产品主体才是别扭的来源。** 三条论证：

### (1) 简陋的判据不是代码量，而是「说没说清它为什么存在」

一个插件要么补真实的缝，要么没有存在理由。本插件的每一条都能一句话说清「DSH 有 X，模型调不到 X」；说不清的都已被删除。**剩下的不是简陋，是窄。** 窄而正确 > 宽而重复。

反过来，「为了不显得简陋而加功能」正是本轮清理掉的那个坏习惯——`dsh-miopiik-policy` 就是这么活到 0.5 的（为将来假设保留代码）。

### (2) DSH 的哲学就是「一切皆插件」，所以薄是正确的形态

DSH 刻意把**原语**（Service/API，宿主提供）与**模型面**（Tool，插件提供）分离。在这套架构里，一个只做适配的插件本来就应该薄。厚插件在这个生态里通常是「和宿主重叠」的信号，不是「功能丰富」的信号。

### (3) 真正厚的东西在别处——而 DSH **完全没有**它

已核实的硬事实：

| 检查 | 结果 |
| --- | --- |
| `grep -rl "\\.dsh/memory"` 全 DSH | **零命中**——DSH 没有这个约定 |
| `ls <DSH> \| grep -i "memory\|recall\|knowledge"` | **零命中**——DSH 没有记忆子系统/包 |
| 官方 `standard` preset 里 "memory" 出现次数 | **0** |
| DSH 全部包 README 里 "long-term/project/persistent memory" | 仅 `dsh-tool-ralph` 一处，与本主题无关 |

而本仓库与用户的实践里已经有一整套**分级记忆与账本协议**：`~/.dsh/memory/global/`（跨项目事实）+ 工作区 `.dsh/memory/`（能力清单、检查点、模型 allowlist）+ `PLAN.md`（计划即执行规格）+ `.dsh/progress/`、`.dsh/contracts/`。这是**从 OMP 迁移并实战检验过的真实方法论**，不是插件代码。

**所以准确的说法是：**

> MiOpIIk **不是**一个简陋的插件；它是一个**厚重的项目方法论**，外加一个刚好够用的适配器。
>
> - **方法论**（本体，不可替代）：工作纪律 + 分级记忆与账本协议。DSH 零覆盖。
> - **适配器**（1 个包 / 5 个工具）：只在 DSH 刻意关闭的少数几处开窄缝。**它薄是设计正确的证据，不是缺陷。**

### 那要不要把它做「厚」？

要，但**不是加插件功能**——是加**文档与可复用性**，而且只做已被实战检验的部分：

1. **把记忆/账本协议写成版本化文档**（`.dsh/memory/` 布局与写入规则、`PLAN.md` 模板、`[EXEC]` 五字段报告格式、验收门格式），让协议成为可交接、可复用的工件，而不是只活在一个人的习惯里。
2. **把这套纪律做成可安装的 preset 声明**（persona + 纪律段落）。DSH 提供 preset **机制**但不提供任何工作流纪律 —— 这是真空档，且不需要写插件代码。
3. **不新增任何与 DSH 重叠的代码。** 加功能前一律先跑 §2 的证据核对。

判据同前：**上游已经做了，做得差也是上游的事；上游没做的，我们只做已被实战检验的那部分。**

## 6. 量化结果

| 指标 | 0.4.1 | 0.5.0 |
| --- | --- | --- |
| 包数 | 9 | **2**（账本独立成包） |
| 模型可见工具 | 11 | **5** |
| 套件 patch 行数 | 4 | **2** |
| 业务源码行数 | 1416 | 1263 |
| 运行时事件钩子 | 5 | 5（3 个 auto-checkpoint + `agent/created` 探测 + 清理） |
